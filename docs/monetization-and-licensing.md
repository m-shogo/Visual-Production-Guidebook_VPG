# マネタイズ方針と、それが設計に与える影響

2026-09-20の議論で決定：**将来的に同業他社へのSaaS販売も見据えて設計する。**

## 決定の中身

- 現時点では自社（映像制作会社）の実務ツールとして使う。
- ただし、将来的に他の映像制作会社にもSaaSとして販売する可能性を排除しない前提で設計する。
- 課金体系（サブスク/都度課金/席数課金など）そのものはまだ決めない。データ構造・UIの検証を優先する。

## この決定が今の設計に与える具体的な影響

「将来SaaS化するかもしれない」からといって、今マルチテナント基盤（組織管理・認証・請求）を作り込むのは時期尚早（破綻防止ルール的にも過剰設計）。今のフェーズで実際に反映したのは次の2点のみ。

### 1. Reference（実在作品の引用データ）の法務確認を必須化する土台を用意した

自社内だけで使っている間は「著作権的にグレーでも、指摘されたら直せばいい」で済むかもしれないが、**他社に販売してカネを取る製品に含まれる引用データ**は法的リスクの質が変わる。他社が有償で使う以上、権利侵害があれば自社の契約責任問題になる。

そのため `schema/reference.schema.json` に `legal_review`（status: pending/approved/rejected）フィールドを追加した。現状は任意項目（社内利用中は空でもよい）だが、**社外顧客向けカタログに含める前には `approved` が必須**というルールをここに明文化しておく。

### 2. データ構造に自社固有の情報をハードコードしない

Technique/Recipe/Reference/Intentのどのスキーマにも「自社名」「自社のプロジェクトID」のような固有情報は持たせていない。将来複数社で使うことになっても、データモデル自体の作り直しは不要なはず（ただし「どの会社のデータか」を分離する仕組み＝マルチテナント機構そのものは、実際に2社目の顧客がついた時点で設計する）。

## 今回あえて作らなかったもの（時期尚早と判断）

- 組織（Organization）・ユーザー・権限のデータモデル
- 課金・プラン管理
- データの公開範囲（自社限定 / 顧客限定 / 全体公開）を制御する仕組み

これらは「他社に売る」という仮説が実際に具体化した時点（少なくとも1社の見込み顧客と話ができた時点）で着手する。今作ると、検証もされていない将来要件のために今の開発速度を落とすだけになる。

## 未決事項

- 課金モデル（サブスク/都度課金/席数）
- 自社データと顧客データをどこまで共有するか（Technique/Recipeのコアカタログは共有資産として売る想定だが、顧客ごとのカスタムRecipeは非公開にすべきか、など）

これらはデータ構造に直接影響しないため、実装を進めながら後回しにしてよい。
